# Project brief for development

This is the development summary of the agreed Milestone 1 proposal. The exact stakeholder-reviewed brief, approval records, and personal validation evidence remain in the private course submission package.

## Product value case

The stakeholder is a developer with applied AI and multi-turn coding-benchmark experience. He rarely chooses coding models based on the task because he does not know which configuration is most suitable. He mainly uses cheaper models when fanning out subagents. He wants to explore agent harnesses and improve his Codex terminal workflow while reducing corrective prompts, completion time, and model cost.

The proposed product is a routing component accessed through a dedicated terminal command. On each newly submitted prompt, Jev or OpenJev receives only that specific prompt as task content, with fixed category instructions, then returns a task type plus a few signals. A separate policy maps those categories to a valid GPT model and reasoning-effort configuration using measured performance, supported settings, and remaining limits. Exact categories will be refined on development examples. Insufficient prompt information triggers an automatic reliable fallback within budget. Codex preserves the repository, tools, approvals, and conversation needed to finish the task; that session context is not sent to the classifier. The OpenRouter analogy means a common routing entry point; a public gateway or billing platform is outside the initial product.

The initial scope is repository bug fixing and debugging. The intended deliverables are a usable router, a cloud-fine-tuned OpenJev classifier, and an evaluation report containing SWE-bench results and strategy comparisons. A small reproducible multi-turn evaluation examines corrective follow-ups, and a stakeholder trial supplies qualitative usability feedback. Feature development, general refactoring, and routing at internal checkpoints are later extensions.

The priority is correct task completion, followed by lower cost and time among similarly reliable configurations. Routing could add latency or make worse choices; savings and quality improvements are hypotheses to test. Reducing the number of prompts means reaching a correct task outcome with fewer corrective user follow-ups, not reducing the number of benchmark tasks.

## Engineering credibility checks

Useful routing requires meaningful differences between available model/effort configurations and enough information in the current prompt to choose among them. Prompt-only classification may be insufficient for vague follow-ups or repository-dependent difficulty; measure that limitation and fallback cost before expensive training. Additional context is a later research option, not an agreed initial input. The project now starts with the hosted TypeSafe Jev client and classification accuracy, followed by Codex integration and measured configuration outcomes. A registry will represent actual supported configurations rather than assuming every model offers interchangeable low/high/off settings.

The model comparison will include a strong fixed GPT configuration, simple routing rules, a cheap learned control, hosted TypeSafe Jev, untuned OpenJev, and fine-tuned OpenJev. Hosted Jev and OpenJev are separate models. The untuned/tuned OpenJev comparison isolates additional training on the same base checkpoint under matched inference conditions. The coding harness, task set, eligible configurations, routing opportunities, and execution limits must be shared across strategies.

Classifier supervision will use reviewed task-type/signal annotations based only on the same current prompt seen at inference. Measured coding outcomes separately inform the category-to-configuration policy. Training, development, and held-out evaluation tasks will be separated, with related turns kept together. Keep session history and later outcomes outside classifier features and annotation inputs. Hold the downstream policy fixed when comparing tuned and untuned OpenJev, and freeze both classifiers and policy before held-out evaluation. Executable checks will determine task success.

SWE-bench will evaluate generated patches on a pinned cohort and evaluator. Standard issue-to-patch runs measure initial selection, so a separate multi-turn protocol is needed to test adaptation across user prompts. That protocol will distinguish required new information from corrective follow-ups, define stopping rules, and withhold hidden checks from routing inputs. Results will include failures and exhausted budgets, repeated runs where affordable, and uncertainty estimates. Scripted prompt counts alone cannot establish human time savings.

The owner reports $3,333 of OpenAI API credits as of the October 2026 planning update, superseding the earlier $3,000 estimate, and wants minimal use for necessary validation, class submissions, and ML-paper experiments. This is not an allocation or independently verified balance. The owner will choose the initial API cap after a run-by-run estimate. Cloud spending must stay strictly under $50 cumulatively; conservatively include other non-OpenAI cash costs until separately reviewed. Linux-server access is believed available but unverified, and no free GPU allocation is confirmed. Routine development should use offline checks and included development tooling where suitable. Local hardware reported during planning is a MacBook Pro with an Apple M5 and 16 GB memory. Fine-tuning is planned on cloud compute; hardware selection requires a compatible recipe, measured memory, and a capped total-job estimate.

The owner has no fixed language preference. Python is selected for the client and later terminal/router and research tooling, with one shared Codex execution path. Source inspection supports a typed app-server client with explicit approval handling; exact published dependency pins and live behavior still need verification. The roadmap retains a small GPT configuration pool and supervised OpenJev adapter training after feasibility checks. Deferred simulated routing/session code is archived locally; the active implementation is the TypeSafe client and preview script. The owner reviews and tests each phase before authorizing the next. The Milestone 2 schedule is inactive.

The owner confirmed research and personal testing as the initial use and Python repositories as the first training/benchmark task domain. Task-repository language is independent of the implementation language. Broader repository coverage and commercial deployment are later decisions.

The owner intends to develop an ML paper and selected the primary question: does fine-tuning OpenJev improve routing over untuned OpenJev, producing better task performance or lower cost/token usage? Multi-turn adaptation remains a secondary analysis. Existing work already studies coding-agent routing and reasoning allocation, so the contribution must be narrower and supported by controlled evidence. Strong controls, held-out data, a predefined reliability margin, paired uncertainty, and training/hosting economics are part of the research plan. The main risks are weak routing signal, overfitting, overhead that outweighs savings, and integration or training costs that exceed resources. Final configurations, cohort sizes, numerical reliability criteria, cloud provider, and verified training pins remain open; neutral or negative results are valid outcomes.
